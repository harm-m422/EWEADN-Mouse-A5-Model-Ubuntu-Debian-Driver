# 官方驱动协议 —— 已破解（2026-10-15）

## 一、怎么破的

官方驱动是 Windows 原生程序，但它走的是 **HID feature report**，
而 Wine 的 winebus 后端就是用 `/dev/hidraw` 的 feature ioctl 跟设备通信的。
所以：**在 Linux 上把官方驱动跑在 Wine 里，再拦它发给 `/dev/hidraw` 的 ioctl**，
就能拿到全部协议。

链路：

```
OemDrv.exe (2,670,080 B, MFC/MSVC2008)
  → HidD_SetFeature / HidD_GetFeature   (Wine 的 hid.dll trace 确认，report_len 520)
  → IOCTL_HID_SET_FEATURE / GET_FEATURE
  → winebus.sys udo 后端
  → ioctl(fd, HIDIOCSFEATURE(520) / HIDIOCGFEATURE(520))   ← LD_PRELOAD shim 拦这里
  → /dev/hidraw9
```

`tools/hidshim.c`（编译成 `hidshim.so`）用 `LD_PRELOAD` 覆盖 `ioctl()`，
只在 `_IOC_TYPE=='H'` 且 `nr` 为 0x06/0x07 时记录设备路径、长度和**完整字节**，
其余请求原样透传。

```bash
gcc -shared -fPIC -O2 -o tools/hidshim.so tools/hidshim.c -ldl
wineserver -k
LD_PRELOAD=./tools/hidshim.so HIDLOG=$PWD/hid.log \
  wine wineprefix/drive_c/eweadn-a5/OemDrv.exe
```

> 也可以直接跑 `bash tools/capture-write.sh`，它会把上面这套流程自动做完。

> `wineserver -k` 是必须的：winebus 跑在常驻的 plugplay 服务里，
> 不先杀掉的话新开的进程不会挂上 shim。

## 二、抓到的报文（原样）

```
SET /dev/hidraw9 len=520  09 0d 05 01 01 00 06 00 00 00 ...
GET /dev/hidraw9 len=520  ret=14
    09 0d 05 01 01 00 06 00 04 00 00 00 00 1a

SET /dev/hidraw9 len=520  09 d6 44 00 01 00 90 01 00 00 ...
GET /dev/hidraw9 len=520  ret=408
    09 58 44 00 01 00 90 01 64 18 04 36 00 13 10 07 00 10 00 17 00 1f 00 3f 00 77 00 ...
```

## 三、协议要点（三条都和我之前的猜测相反）

| 项 | 实测 | 我之前错在哪 |
|---|---|---|
| **feature report ID** | **`0x09`** | 一直在敲 5 和 6 |
| **缓冲长度** | **固定 520**（1 字节 report ID + 519 数据） | 试过 8 / 6 / 16 / 64，试 520 时因为缺 SET 而失败 |
| **时序** | **必须先 SET 命令、再 GET 响应** | 单独 GET 被 stall（EPIPE），于是误判整条通道是死的 |

520 这个数字和 HID 描述符完全吻合：接口 1.1 里 **Feature report id=9 声明 519 字节**。

而且 libratbag 的 `SINOWEALTH_CONFIG_REPORT_SIZE` 正好是 **520** —— 说明这确实是
Sinowealth 协议族，只是 report ID 是 9、命令字节不一样。

## 四、已确认的两条读命令

### A. 设备信息

```
请求 09 | 0d 05 01 01 00 06 00 | 00 ×512
响应 09 | 0d 05 01 01 00 06 00 | 04 00 00 00 00 1a
       ↑    ↑ 回显命令 7 字节        ↑ 型号标识 6 字节
```

最后 6 字节 = `04 00 00 00 00 1a`，**正好等于 `Cfg.ini` 里 EWEADN A5 的 `Psd=4,0,0,0,0,1a`**；
A5 PRO 是 `...,0x29`、A5 Ultra 是 `...,0x1D`。所以这条命令就是"读型号标识"。

### B. 读配置

```
请求 09 | d6 44 00 01 00 90 01 | 00 ×512
响应 09 | 58 44 00 01 00 90 01 | <配置数据，本机 372 字节有效>
```
响应字节 1（`58`）和请求字节 1（`d6`）不同，其余 2..7 字节回显。

配置体（偏移从响应第 0 字节算）：

| 偏移 | 内容 |
|---|---|
| 0x00 | report ID `09` |
| 0x01 | `58`（状态/校验，待定） |
| 0x02..0x07 | 回显请求的 6 字节 |
| 0x08..0x0E | `64 18 04 36 00 13 10`（用途待定） |
| **0x0F..0x1A** | **6 个 u16LE：DPI 档位（X 轴）** |
| 0x1B..0x22 | 10 字节 0 |
| **0x23..0x2E** | **6 个 u16LE：DPI 档位（Y 轴，XY 独立）** |
| 0x2F..0x37 | 0 |
| 0x38 起 | 各档 LED 颜色（每档 21 字节，含 `44 01` 前缀和 `ff/00/40` 颜色分量） |

本机读到的 DPI raw 值（两组相同）：`7, 16, 23, 31, 63, 119`
→ 按 `DPI = (raw+1)*100` 得 **800 / 1700 / 2400 / 3200 / 6400 / 12000**。

> 第 2 档是 1700 而不是 `Cfg.ini` 默认的 1600 —— 需要拿驱动 UI 上显示的数字对一下，
> 才能确定编码是 `(raw+1)*100` 还是别的。**这个待确认。**

## 五、已验证：本工具能复现

```bash
python3 a5tool.py read --parse
```

在 `/dev/hidraw9`（有线 258a:0136 的接口 1.1）上复现成功，返回与官方驱动抓包
**逐字节一致**的 14 字节设备信息，以及 372 字节配置。

两个身份的表现：

| 节点 | 设备信息 | 读配置 |
|---|---|---|
| `/dev/hidraw9` 有线 iface 1.1 | ✅ 14 字节 | ✅ 372 字节 |
| `/dev/hidraw6` 有线 iface 1.0 | ❌ EPIPE | — |
| `/dev/hidraw5` 接收器 iface 1.1 | ❌ ETIMEDOUT | — |
| `/dev/hidraw4` 接收器 iface 1.0 | ❌ EPIPE | — |

**即：配置通道只在线模式的接口 1.1 上，必须插 Type-C 线。**
（接收器身份上官方驱动也只发了另一条短命令 `09 09 07 00 01 00 01 00`，没读到配置。）

## 六、还缺：写命令

抓包时官方驱动只做了**读**（启动时载入配置），没有触发写。
写命令需要让驱动真的去改设置，所以用 `capture-write.sh`：
在 Wine 窗口里改一项设置并应用，shim 会把写入报文记下来。

拿到写命令后就能把 `set`（DPI / 回报率 / LED / 改键）做进 `a5tool.py`，
变成纯 Linux 原生工具。

## 七、写协议（已抓包并验证）

抓包方法见 `capture-write.sh`：在 Wine 窗口里把第 1 档 DPI 从 800 改成 1000 并应用。
**关键前提：脚本必须先 `wineserver -k`** —— winebus 的 HID 后端跑在常驻的 plugplay
服务进程里，残留的旧进程没加载 shim，就什么都抓不到（第一版脚本就栽在这里）。

### 抓到的写报文

```
读响应  ret=408  09 48 44 00 01 00 90 01 64 18 04 26 00 13 10 07 00 10 00 17 00 1f 00 3f 00 77 00 ...
写入    len=520  09 fa 04 00 01 00 90 01 64 18 04 26 00 13 10 07 00 09 00 17 00 1f 00 3f 00 77 00 ...
```

逐字节 diff，**372 字节里只有 4 处不同**：

| 偏移 | 读 | 写 | 含义 |
|---|---|---|---|
| 0x001 | `48` | `fa` | 写命令字节 |
| 0x002 | `44` | `04` | 写命令字节 |
| 0x011 | `10` | `09` | 第 2 档 DPI：16 → 9 |
| 0x025 | `10` | `09` | Y 组同位 |

**所以写协议 = 拿读响应当模板，就地改上面 3 个字节，补零到 520，`SET(9, 520)`。**

### DPI 编码

`raw = DPI/100 - 1`（实测：设成 1000 → raw 变成 9 = 1000/100-1；设成 800 → 7）。
反算 `DPI = (raw+1)*100`，所以 **DPI 必须是 100 的倍数**。

### ⚠️ 一个坑：缓冲不能错位

写入必须**就地**改读响应，**不能把响应挪到 `buf[1:]`** —— 那会让从第 3 字节起
整体错位一字节，设备直接 NAK（`ETIMEDOUT`）。

实测对照：
```
原样重放官方抓到的字节       -> OK / OK / OK    （三次全成功）
我的错位版本                 -> E110:ETIMEDOUT
修复后逐字节比对官方抓包      -> 完全一致
```

## 八、现状：Linux 原生工具可用

```bash
# 只读：设备信息 + 完整配置 + DPI 解析
python3 a5tool.py --dev 9 read --parse

# 只改一档
python3 a5tool.py --dev 9 set --slot 1 --value 900

# 一次设 6 档
python3 a5tool.py --dev 9 set --dpi 800,1600,2400,3200,6400,12000

# 只看会发什么，不写
python3 a5tool.py --dev 9 set --dpi ... --dry-run
```

真机验证记录（可逆测试）：

```
当前 raw=[7, 9, 23, 31, 63, 119] -> [800, 1000, 2400, 3200, 6400, 12000]
set --slot 1 --value 900  -> 写入成功, 回读 raw=[8, 9, ...] -> [900, ...]   ✅
set --slot 1 --value 800  -> 写入成功, 回读 raw=[7, 9, ...] -> [800, ...]   ✅
set --dpi 800,1600,...    -> 写入成功, 回读 raw=[7, 15, ...] -> [800,1600,...] ✅
set --slot 1 --value 950  -> 正确拒绝（不是 100 的倍数）
```

**前提：必须插 Type-C 线**（配置通道只在线模式的接口 1.1 = `/dev/hidraw9`）。

## 九、还没做的

- **回报率**：配置体 0x08..0x0E 那 7 个字节（`64 18 04 26 00 13 10`）用途待定，回报率可能在附近
- **LED 颜色**：0x38 起，每档 21 字节，含 `44 01` 前缀和 `ff/00/40` 颜色分量
- **按键重映射**：`Cfg.ini` 的 `[KEY]` 段有 12 个键位的默认值，协议里对应的命令还没抓
- **设备端烧写**：写完是否需要额外 commit 命令（实测直接生效，不需要）

要把这些补完，只要在 Wine 窗口里改对应设置、用 `capture-write.sh` 再抓一次即可。
